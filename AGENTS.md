# Ys III consumer ownership

Read `README.md`, `docs/STATUS.md`, `docs/DEVELOPMENT.md` and `toolchain.json`
before implementation. Inspect and preserve existing work. Make routine choices
autonomously; report evidence and limitations candidly.

This project owns Ys III configuration, source/overlay discovery, measured
native coverage, game adapters/enhancements, launcher integration and bounded
gameplay/campaign verification. `rages4calm/pcenginerecomp` owns shared CPU and
device semantics, media, code generation and reusable host features. Reuse its
verified implementation; do not maintain a runtime fork or patch its active
working tree. Send focused shared-tool defects upstream and upgrade pins only
after affected checks. Do not use a workbench workflow.

Public files contain authored source, configuration, documentation and synthetic
tests only. Keep ROM/BIOS bytes, extracted data, translated game code, code
captures, screenshots, states, saves, local paths and chat coordination private.
Never stage `.local/`, `.deps/` or build outputs. Run the publication audit on the
staged file set before every push. Review the diff as well.

Owner inputs are read-only. Never download substitutes, alter originals, or use
owner installations/saves. Initial authentic-format blank BRAM is an explicitly
selected immutable seed; guest writes are volatile. Cross-process persistence
needs a separate implementation and test.

Do not use a per-batch storage quota, budget scanner or accounting workflow.
Reuse immutable inputs/dependencies, preserve qualified evidence, retain
replayable receipts and stop owned processes. Do not delete unrelated files.

Use TCP guest controls/captures for bounded verification. Keep built, executed,
rendered, independent-reference and native-qualified evidence separate. Report
native/interpreted retired instruction counts and unresolved source variants;
emission counts alone prove no execution. Preserve logical PC, all MPRs and
source identity when discovering or selecting overlays. Capture original game
code only in unmodified or verified-restored state, never temporary cheat bytes.

The owner authorizes verified minimal development assists. Verify exact input
and independent-reference evidence, journal expected-byte edits, preserve
unassisted checkpoints, and label assisted progression separately. An assisted
encounter is not campaign completion. The explicit unknown-CD `gear-good`
response profile remains a visible compatibility condition, not implemented
unknown-command semantics or hardware qualification.

Peer chat IDs, defect reports and receipt paths belong in private coordination
metadata. The owner authorized messaging only the specific toolkit chat recorded
there. One report per material change; no unchanged pinging. Reports must name
tool/build/input identities, execution tier, PC/MPR/source, bounded recipe,
expected/observed behavior, independent evidence and limits, and private receipts.

Subagents may be used with explicit file ownership. They share this checkout;
never revert others' work. Run meaningful synthetic tests, affected upstream
checks and the retained private route when changing the native module contract.
